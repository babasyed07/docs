---
title: "Deploy on an Existing Amazon EKS Cluster"
---
Use this page with agentcoreeks.zip. The stack does not create an EKS cluster. Instead, it creates an IRSA pod role, a Secrets Manager secret, a read-only discovery policy, a token-read policy, and an ECR pull policy for the node roles you specify.

## How the pieces fit

- Pod IAM role. The reva-agentcore service account assumes this role using a web-identity token from the cluster OIDC provider. The trust policy allows only that service account in the namespace you specify.

- Secrets Manager. The secret holds the Reva API token. The container reads it using the pod role. The token is not stored in the Helm values.

- Node pull access. The node IAM role, or the Fargate pod execution role, pulls the image. The pull policy is attached to these roles, not to the pod role.

## Deploy the permissions stack

Deploy customer-eks-permissions.json in the account and region where the EKS cluster runs. The namespace you specify here must match the namespace you later specify in Helm. The README example uses rtg, while the template default is reva-agentcore. Choose one and use it in both places. The service account name must be reva-agentcore in the stack, chart, and customer-values.yaml.

```bash
CLUSTER_NAME="<YOUR_EKS_CLUSTER_NAME>"
CLUSTER_REGION="<YOUR_CLUSTER_REGION>"
NAMESPACE="rtg"
SERVICE_ACCOUNT="reva-agentcore"
STACK_NAME="reva-agentcore-permissions"

OIDC_ISSUER=$(aws eks describe-cluster --name "$CLUSTER_NAME" --region "$CLUSTER_REGION" \
  --query "cluster.identity.oidc.issuer" --output text)
OIDC_PROVIDER="${OIDC_ISSUER#https://}"

NODE_ROLE_NAMES="<YOUR_EKS_NODE_ROLE_NAME>"

aws cloudformation deploy \
  --stack-name "$STACK_NAME" \
  --region "$CLUSTER_REGION" \
  --template-file customer-eks-permissions.json \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides \
    OidcProviderHostPath="$OIDC_PROVIDER" \
    KubernetesNamespace="$NAMESPACE" \
    ServiceAccountName="$SERVICE_ACCOUNT" \
    ImagePullRoleNames="$NODE_ROLE_NAMES" \
    PublisherRepositoryArn="arn:aws:ecr:us-east-1:<REVA_ECR_ACCOUNT_ID>:repository/ecr-awsaiworkloadconnectorsvc" \
    TokenSecretName="reva/${CLUSTER_NAME}/store-token" \
    AllowedRegions="us-east-1,us-west-2"
```

AllowedRegions is the list of regions in which the IAM role may call the regional discovery APIs. By default, the CloudFormation template sets this parameter to us-east-1 and us-east-2. If you leave the parameter unset, the role can use Bedrock, AgentCore, Lambda, the agent registry, and CloudTrail only in those two regions. Change AllowedRegions to the regions the customer wants to permit, and set it to the same regions entered on the integration form. Do not replace the default with every AWS region. Requests to regions outside this list are denied, even if those regions are specified on the integration form. IAM reads remain global and are not limited by this list. In ImagePullRoleNames, provide every node role on which the pod can be scheduled, separated by commas. Do not include the IRSA role in this list.

Register the cluster's IAM OIDC provider before deploying the stack. OidcProviderHostPath is the issuer host and path with https:// removed and no trailing slash.

Narrow the two patterns if you do not want the role to read every role and function:

- AgentRoleNamePattern defaults to *. For example, use AmazonBedrockAgentCore* or agentcore/* as a narrower value.

- FunctionNamePattern defaults to *. For example, use agentcore-*.

- EnableModelCallCorrelation defaults to false. Set it to true only if you want to grant cloudtrail:LookupEvents so the connector can associate agents with the models they call.

- Leave ExistingTokenSecretArn empty to let the stack create the secret. If the secret already exists, set this parameter and leave TokenSecretName unused. The stack does not modify an existing secret.

- Set TokenSecretKmsKeyArn if the secret must use a customer-managed key. The pod role then receives kms:Decrypt permission only through Secrets Manager and only for that secret.

Read the outputs you need for Helm:

```bash
POD_ROLE_ARN=$(aws cloudformation describe-stacks --stack-name "$STACK_NAME" --region "$CLUSTER_REGION" \
  --query "Stacks[0].Outputs[?OutputKey=='PodRoleArn'].OutputValue | [0]" --output text)

TOKEN_SECRET_ARN=$(aws cloudformation describe-stacks --stack-name "$STACK_NAME" --region "$CLUSTER_REGION" \
  --query "Stacks[0].Outputs[?OutputKey=='TokenSecretArn'].OutputValue | [0]" --output text)
```

The stack also outputs DiscoveryPolicyArn, TokenReadPolicyArn, and ImagePullPolicyArn. ImagePullPolicyArn is attached to the node roles, while the other two are attached to the pod role.

## Put the Reva token in the secret

A new secret is created with a generated placeholder in the JSON field STORE_API_TOKEN. Replace it with the OAuth Token copied in Open the integration. The value must be a JSON object. Keep the field name as STORE_API_TOKEN unless you also set STORE_TOKEN_SECRET_KEY to a different field name.

```bash
aws secretsmanager put-secret-value \
  --region "$CLUSTER_REGION" \
  --secret-id "$TOKEN_SECRET_ARN" \
  --secret-string '{"STORE_API_TOKEN":"<PASTE_THE_OAUTH_TOKEN>"}'
```

## Configure Helm and install

Edit customer-values.yaml:

- aws.region is the cluster region.

- serviceAccount.roleArn is the PodRoleArn output.

- secrets.tokenArn is the TokenSecretArn output. The chart writes this value into the container as REVA_TOKEN_ARN.

- env.REVA_API_BASE_URL and env.SERVICE_DATAINGESTIONREST_URL are the tenant API host. The file ships with https://api.reva.ai.

- Add STORE_TOKEN_SECRET_ARN under env and set it to the same TokenSecretArn. The connector reads the token using this variable.

The env block in customer-values.yaml needs the following entry in addition to the values already in the file:

```bash
env:
  PORT: "8055"
  LOG_LEVEL: "INFO"
  REVA_API_BASE_URL: "https://api.reva.ai"
  SERVICE_DATAINGESTIONREST_URL: "https://api.reva.ai"
  STORE_TOKEN_SECRET_ARN: "<TOKEN_SECRET_ARN>"
  AGENTCORE_STATE_MODE: "ephemeral"
```

Set STORE_TOKEN_SECRET_KEY in the same env block only if the JSON field is not named STORE_API_TOKEN. If the variable is unset, the connector reads the STORE_API_TOKEN field. To use your own secret, set STORE_TOKEN_SECRET_ARN to that secret's ARN and STORE_TOKEN_SECRET_KEY to the field containing the token. The pod role must have permission to call secretsmanager:GetSecretValue on that ARN. Passing an existing ARN as ExistingTokenSecretArn at deployment time grants this access without requiring you to edit the policy afterward.

```bash
helm upgrade --install reva-agentcore ./chart \
  --namespace rtg --create-namespace \
  --values customer-values.yaml
```

The release runs one replica and uses the Recreate strategy. The service account name in the chart is reva-agentcore. The pod runs as UID 10001, with a read-only root filesystem, and does not mount the Kubernetes API token. Requests are 100m CPU and 128Mi memory. Limits are 1 CPU and 512Mi.

## Check the pod

```bash
kubectl get pods -n rtg
kubectl -n rtg logs deployment/reva-agentcore --tail=100
```

A healthy start logs that the connector is listening on :8055. If the pod cannot pull the image, either the node role is missing from ImagePullRoleNames or the publisher repository policy does not allow that role. If the pod starts but the import returns unauthorized, the secret still contains the placeholder, or STORE_TOKEN_SECRET_ARN does not point to the correct secret.
