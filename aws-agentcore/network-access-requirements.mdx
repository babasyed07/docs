## Reva destinations

| Destination | Hostname | Connects from | Purpose |
| --- | --- | --- | --- |
| Reva console | The tenant console, for example `<your-tenant-console-url>` (HTTPS, TCP 443) | Browsers of the people who create the integration | Create the AI Workload integration, copy the OAuth token, and download the deployment zip. |
| Reva API | The value of REVA_API_BASE_URL. The packages default to api.reva.ai (HTTPS, TCP 443). | The connector pod or ECS task | Load this integration's configuration, then push discovered entities. The connector calls POST /ingestion/v1/getExternalConnectorDetails with the token as a bearer credential. |

Set REVA_API_BASE_URL to the API host provided by Reva for the tenant. On ECS, this is the CloudFormation parameter RevaApiBaseUrl. On EKS, it is env.REVA_API_BASE_URL in customer-values.yaml.

## Port 8055

The connector listens on TCP 8055 inside the pod or task. Operators use this port to start an import. It is not a Reva callback.

- EKS. The Helm chart does not create a Kubernetes Service (service.enabled is false). Use kubectl exec to call http://localhost:8055/initImport. The port is not published through a load balancer.

- ECS. The template creates a security group that allows TCP 8055 from 0.0.0.0/0 and allows all egress. Restrict the ingress CIDR to the operator network or a bastion before using the stack in an account where 0.0.0.0/0 is unacceptable. It is also fine to leave the task without an inbound path to port 8055 if imports are started using ECS Exec against localhost.

If you use VPC endpoints instead of a NAT gateway, they must cover ECR (api and dkr), S3, Secrets Manager, STS, IAM, CloudWatch Logs, Bedrock, Bedrock AgentCore, and Lambda. The Reva API is not an AWS service, so it still requires NAT or an egress proxy.
