---
title: "Okta Token Inline Hook"
description: "Configure Okta to request policy-authorized access-token and ID-token claims from Reva during token issuance."
---

The Okta Token Inline Hook lets Okta request token enrichment from Reva while issuing an access token or ID token. Reva resolves the request context, evaluates the active Cedar policies in the selected policy store, and returns Okta claim patch commands.

This endpoint is an Okta callback, not a general-purpose API for application code. Configure Okta with the values generated by Reva instead of constructing credentials yourself.

## Endpoint

| Method & path | Purpose |
|---|---|
| `POST /pdp/hooks/okta/v1/token` | Evaluate an Okta token-transform event and return authorized claim patches. |

The base URL is your tenant's API Gateway host, such as `https://api.pr06.preview.reva.ai` for Preview or `https://api.dv06.dev.reva.ai` for Development.

## Configure the hook

Open the token-enrichment policy store and go to **Settings → Identity & Token Setup → Token Enrichment Integration**. Copy these values into the Okta Token Inline Hook configuration:

| Reva value | How it is used |
|---|---|
| **Inline Hook URL** | The complete callback URL that Okta calls. |
| **Authentication Field** | The HTTP header name for hook authentication. |
| **Authentication Secret** | The gateway credential sent as the raw value of the Authentication Field. |
| **Custom Header Field Name** | The policy-store header name, normally `policyStoreId`. |
| **Custom Header Value** | The policy store identifier used for evaluation. |

Use the exact Authentication Secret shown in Reva. Do not add a `Bearer` prefix unless the value displayed by Reva includes one. See [Configure Token Enrichment Settings](/token-enrichment-settings#token-enrichment-integration) for the complete setup flow.

<Warning>
  Treat the Authentication Secret as a credential. Do not paste a real value into documentation, source control, support tickets, or request examples. Rotate it in Reva if it is exposed.
</Warning>

## Request contract

Okta sends a JSON event whose `eventType` must be `com.okta.oauth2.tokens.transform`. The request can contain user, session, OAuth client, access-token, and ID-token context.

Send the Okta event body unchanged. Reva accepts additional standard Okta fields and retains them so policy-store context mappings can read configured JSON paths.

The generated API reference provides two sanitized `authorization_code` examples:

| Example | `data.access.claims.role_model` | `data.access.claims.app_code` |
|---|---|---|
| **IBM LDAP role model** | `ibm-ldap` | Synthetic application code |
| **Okta role model** | `okta` | Synthetic application code |

These are two payload examples for the same endpoint and schema. They are not separate APIs.

`role_model`, `app_code`, and other custom claims do not select a different route or request type. Reva can make them available to Cedar only when the policy store's context mappings reference their JSON paths.
Each example also includes a sanitized `identity.claims` token set to show that the same request can carry both access-token and ID-token context.

For a `client_credentials` request, Reva reads the OAuth client identifier from the protocol request or client context and evaluates it as a machine or application principal. End-user and session context can be absent in that flow.

## Response contract

A successful response always contains a `commands` array. Reva can return:

| Command type | Token target |
|---|---|
| `com.okta.access.patch` | Access token |
| `com.okta.identity.patch` | ID token |

Each command contains `add` or `replace` operations for paths such as `/claims/roles`.

```json
{
  "commands": [
    {
      "type": "com.okta.access.patch",
      "value": [
        {
          "op": "add",
          "path": "/claims/roles",
          "value": ["example-role"]
        }
      ]
    }
  ]
}
```

If no claim is authorized or enrichment cannot be completed, the endpoint can fail open with HTTP `200` and an empty command list:

```json
{
  "commands": []
}
```

An empty list means Okta can continue token issuance without adding Reva claims. It does not confirm that enrichment succeeded.

## Request errors

| Status | Meaning |
|---|---|
| `400` | The JSON is invalid, the event type is unsupported, or the policy store identifier is missing and cannot be resolved from configuration. |
| `401` | The configured Authentication Secret is missing or invalid. |

Use Okta's inline-hook testing flow and [Validate Token Enrichment](/validate-token-enrichment) to verify the complete integration without publishing credentials or real token payloads.
