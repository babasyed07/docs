---
title: "Developer Integration — Evaluation API"
description: "Call the Reva PDP directly to authorize agent-chain calls without the SDK."
---

If you can't (or don't want to) embed the [`reva-ai` SDK](/ai-workload-developer-sdk), call the Reva PDP from your own enforcement point. You send the details of a call — who is calling, what they're doing, on what resource, with what context — and the PDP returns an allow/deny decision.

| Approach | Use when |
|:---------|:---------|
| **SDK** ([guide](/ai-workload-developer-sdk)) | You control the agent code and want drop-in inbound/outbound authorization. |
| **Evaluation API** (this page) | You enforce at a gateway/proxy, use an unsupported language, or want full control over the request. |

## Endpoints

The `reva-ai` SDK calls these PDP endpoints at runtime; you can call them directly too:

| Method & path | Purpose |
|:--------------|:--------|
| `POST {RTG_URL}/pdp/access/v1/agent/evaluation` | Evaluate a single agent-chain call and return **allow / deny**. |
| `POST {RTG_URL}/pdp/access/v1/token/enrich` | Evaluate an outbound hop and, on allow, mint a short-lived **transaction token**. |

<Note>
  The browsable, generated reference for the PDP Edge API (the `authorize` and `search` operations) is under the **[API Documentation](/api-reference/introduction)** tab. The agent-evaluation and token-enrichment paths above are the runtime endpoints used by the SDK — confirm the exact base URL (`RTG_URL`) and path prefix for your tenant.
</Note>

## Authentication

| Item | How it's sent |
|:-----|:--------------|
| Platform API key | `X-API-Token` header on every PDP call (`RTG_AUTH_TOKEN`) |
| Caller identity | The end user's bearer token / inherited transaction token |
| Policy store | The store the call is evaluated against (`POLICYSTORE_ID`) |

## Request Fields

| Field | Description |
|:------|:------------|
| `subject` | Who is making this call — `{ type, id }` (`User` or `Agent`), plus optional `properties` (e.g. `origin`). |
| `action` | The operation — `{ "name": "invokeAgent" \| "invokeTool" \| "invokeModel" }`. |
| `resource` | What is being called — `{ type, id, name, properties }`. For tools, includes the MCP endpoint and `tool`. |
| `principal` | The originating end user the chain runs for. |
| `context.onBehalfOf` | The delegating user and attributes (e.g. `riskTier`) — drives on-behalf-of policies. |
| `context.environment` | `requestId`, `time`, `sourceIp`, `geo`. |
| `transmission` | The prompt/intent of the call — `promptKey`, `role`, `contentType`, `content`. |
| `session` | Conversation correlation — `id` (thread), `turn`, `startedAt`. |
| `history` | The prior hop(s), recursively, for chain-of-custody. `null` at the first hop. |

## Responses

On **allow**, evaluation returns a positive decision; `token/enrich` additionally returns a short-lived transaction token to forward on the next hop:

```json
{ "decision": true }
```

On **deny**, the decision is negative and a reason is included so you can diagnose the policy outcome:

```json
{
  "decision": false,
  "context": { "reason": "authorization denied by policy" }
}
```

Every decision — allow or deny — appears in the [decision logs](/ai-workload-decision-logs), correlated by the session `threadId`.
