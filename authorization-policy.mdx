This example shows how to build a simple authorization policy in Reva for a sample **PetStore** application.

You will create a policy that allows a specific user, **John**, to perform two actions on the PetStore application:

* `ListOrders`
* `GetStoreInventory`

You will also upload test data, test the policy, review the Access Map, check impact analysis, and publish the policy.

## Example scenario

The PetStore application has users who can perform actions on the PetStore application resource.

In this example:

| Component | Example value                             | Description                                   |
| --------- | ----------------------------------------- | --------------------------------------------- |
| Principal | `John`                                    | The user requesting access                    |
| Actions   | `ListOrders`, `GetStoreInventory`         | The operations John is allowed to perform     |
| Resource  | `PetStore`                                | The application resource being accessed       |
| Condition | User is active and application is enabled | Optional checks used before access is allowed |

## Before you begin

Before creating the policy, make sure you have a custom application policy store.

You can use either authorization path:

| Authorization path                        | Use this when                                                 |
| ----------------------------------------- | ------------------------------------------------------------- |
| Amazon Verified Permissions Authorization | You want to publish the policy to Amazon Verified Permissions |
| Cedar Authorization                       | You want to publish the policy to Git or Reva Managed         |

To create the custom application policy store, go to **Manage Policies > Create > Custom Application**.

For more details, see [Onboard a Custom Application](/custom-application-authorization/onboard-custom-application).

## Step 1: Start custom application onboarding

1. Go to **Manage Policies**.
2. Select **Create**.
3. Select **Custom Application**.
4. Enter the policy store name and description.
5. Select the portfolio.
6. Select the application owner.
7. Choose the policy format:
   - Select **AVP** if you want to publish to Amazon Verified Permissions.
   - Select **Cedar** if you want to publish to Git or Reva Managed.
8. Continue to the schema onboarding step.

## Step 2: Define the schema during onboarding

For this PetStore example, create the schema manually during the onboarding flow.

The schema should define the application access model.

| Schema element | Name | Description |
|---|---|---|
| Principal | `User` | Represents a user who requests access |
| Resource | `Application` | Represents the PetStore application |
| Actions | `ListOrders`, `GetStoreInventory` | Actions that can be performed on the PetStore application |
| User attribute | `status` | Used to check whether the user is active |
| Application attribute | `status` | Used to check whether the application is enabled |

### Manual schema steps

1. In the schema onboarding flow, select the manual schema design option.
2. Create the principal type `User`.
3. Add the `status` attribute to `User`.
4. Create the resource type `Application`.
5. Add the `status` attribute to `Application`.
6. Create the actions:
   - `ListOrders`
   - `GetStoreInventory`
7. Map the actions to the `Application` resource.
8. Review the schema.
9. Accept the schema.

<Note>
For a new policy store, the schema must be accepted before the policy store onboarding flow can be completed and before policies can be created.
</Note>

## Step 3: Complete policy store onboarding

After the schema is accepted, complete the policy store onboarding flow.

Depending on the product flow, Reva may next show AI-suggested policies or ask whether you want to start policy design or upload test data.

| Option | Result |
|---|---|
| Add AI-suggested policies | Adds selected starter policies generated from the schema |
| Skip suggested policies | Continues without adding starter policies |
| Start Policy Design | Opens the Policy Designer |
| Upload Test Data | Opens the Data tab so you can upload test data |

For this example, continue with **Upload Test Data** so you can test the policy and build the Access Map.

## Step 4: Add test data

After accepting the schema, add test data so you can test the policy and build the Access Map.

1. Open the policy store.
2. Go to the **Data** tab.
3. Select **Test Data**.
4. Download the data template.
5. Add sample data for users and applications.
6. Upload the completed test data file.

Use data similar to the following.

| Entity type | Entity ID           | Attribute | Value      |
| ----------- | ------------------- | --------- | ---------- |
| User        | `john`              | `status`  | `Active`   |
| User        | `mary`              | `status`  | `Active`   |
| User        | `david`             | `status`  | `Inactive` |
| Application | `petstore`          | `status`  | `Enabled`  |
| Application | `petstore-disabled` | `status`  | `Disabled` |

<Note>
Policy testing and Access Map depend on both policies and data. If test data is missing or does not match the schema, policy tests and Access Map results may not show the expected access relationships.
</Note>

## Step 5: Open the Policy Designer

1. Open the policy store.
2. Go to the **Policies** tab.
3. Select **Start Policy Design**.
4. Create a new policy using one of the available authoring methods.

Reva supports the following policy design options.

| Authoring option | Description                                                  |
| ---------------- | ------------------------------------------------------------ |
| Create with AI   | Use natural language instructions to generate a Cedar policy |
| Edit with AI     | Select an existing policy and ask Reva AI to update it       |
| Code editor      | Write or edit the Cedar policy manually                      |

## Step 6: Create the policy with AI

Use the following instruction in Reva AI:

```text
Allow user John to list orders and get store inventory for the PetStore application only when the user status is Active and the application status is Enabled.
```

Review the generated policy before saving it.

The policy should express this intent:

| Policy part | Expected value                            |
| ----------- | ----------------------------------------- |
| Effect      | Permit                                    |
| Principal   | John                                      |
| Actions     | `ListOrders`, `GetStoreInventory`         |
| Resource    | PetStore application                      |
| Condition   | User is active and application is enabled |

## Step 7: Review the Cedar policy

The generated policy should look similar to this example.

```cedar
permit (
  principal == PetStore::User::"john",
  action in [
    PetStore::Action::"ListOrders",
    PetStore::Action::"GetStoreInventory"
  ],
  resource == PetStore::Application::"petstore"
)
when {
  principal.status == "Active" &&
  resource.status == "Enabled"
};
```

<Note>
The exact namespace and entity names depend on the schema created in your policy store. If your schema uses different names, update the policy to match the accepted schema.
</Note>

## Step 8: Test the policy

Before publishing, test the policy with multiple scenarios.

1. Go to the **Policies** tab.
2. Select the policy.
3. Select **Test**.
4. Choose the principal, action, resource, and context.
5. Run the test.
6. Review the authorization result.

Use these test cases.

| Test case                           | Principal | Action              | Resource            | Expected result |
| ----------------------------------- | --------- | ------------------- | ------------------- | --------------- |
| John lists orders                   | `john`    | `ListOrders`        | `petstore`          | Permit          |
| John gets store inventory           | `john`    | `GetStoreInventory` | `petstore`          | Permit          |
| Mary lists orders                   | `mary`    | `ListOrders`        | `petstore`          | Deny            |
| John performs an unsupported action | `john`    | `DeleteOrder`       | `petstore`          | Deny            |
| Inactive user lists orders          | `david`   | `ListOrders`        | `petstore`          | Deny            |
| John accesses disabled application  | `john`    | `ListOrders`        | `petstore-disabled` | Deny            |

## Step 9: Review Access Map

Use **Access Map** to visualize the access relationships created by the policy and test data.

In this example, Access Map should show that:

| Principal | Action              | Resource |
| --------- | ------------------- | -------- |
| John      | `ListOrders`        | PetStore |
| John      | `GetStoreInventory` | PetStore |

Access Map should not show Mary or David as having access to the PetStore actions unless additional policies grant them access.

For more information, see [Use Access Map](/use-access-map).

## Step 10: Review impact analysis

Before publishing, review the impact of the policy change.

Impact analysis helps you understand how the policy affects access before the change is published.

Review:

| Review item       | What to check                                            |
| ----------------- | -------------------------------------------------------- |
| New access        | John receives access to the expected actions             |
| Unintended access | Other users do not receive access                        |
| Deny scenarios    | Inactive users and disabled applications are not allowed |
| Access Map        | Access relationships match the intended policy behavior  |

For more information, see [Policy Testing and Impact Analysis](/policy-testing-and-impact-analysis).

## Step 11: Publish the policy

After testing and impact review, publish the policy to the configured destination.

The publish destination depends on the policy store type.

| Policy store type | Publish destination         |
| ----------------- | --------------------------- |
| AVP               | Amazon Verified Permissions |
| Cedar             | Git or Reva Managed         |

### Publish to AVP

Use this path when the policy store type is AVP.

1. Open the AVP policy store.
2. Go to **Settings**.
3. Select **Policy Store Configuration**.
4. In **Policy Distribution**, confirm that the publish destination is **AVP**.
5. Return to the **Policies** tab.
6. Review the policies.
7. Select **Publish**.
8. Verify the publish status.

See [Publish to AVP](/custom-application-authorization/avp-authorization/publish-to-avp).

### Publish to Git

Use this path when the policy store type is Cedar and the publish destination is Git.

1. Open the AVP policy store.
2. Go to **Settings**.
3. Select **Policy Store Configuration**.
4. In **Policy Distribution**, confirm that the publish destination is **AVP**.
5. Return to the **Policies** tab.
6. Review the policies.
7. Select **Publish**.
8. Verify the publish status.

See [Publish to Git](/custom-application-authorization/cedar-authorization/publish-to-git).

### Publish to Reva Managed

Use this path when the policy store type is Cedar and the publish destination is Reva Managed.

1. Open the Cedar policy store.
2. Go to **Settings**.
3. Select **Policy Store Configuration**.
4. In **Policy Distribution**, confirm that the publish destination is **AVP**.
5. Return to the **Policies** tab.
6. Review the policies.
7. Select **Publish**.
8. Verify the publish status.

See [Publish to Reva Managed](/custom-application-authorization/cedar-authorization/publish-to-reva-managed).

## Step 12: Verify after publishing

After publishing, verify that the policy behaves as expected.

| Area                   | What to verify                                                      |
| ---------------------- | ------------------------------------------------------------------- |
| Publish status         | Confirm that the publish operation completed successfully           |
| Policy version         | Review the published version in Version History                     |
| Authorization behavior | Test the expected permit and deny scenarios                         |
| Decision Logs          | Review authorization decision activity after runtime traffic starts |
| Access Map             | Confirm that access relationships still match the intended model    |

## Troubleshooting

| Issue                             | Possible cause                                          | Recommended action                                                  |
| --------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------- |
| Policy cannot be saved            | The policy references schema elements that do not exist | Review the schema and update the policy                             |
| Policy test returns deny for John | Test data does not match the policy condition           | Confirm that John is active and the PetStore application is enabled |
| Policy test allows the wrong user | The principal condition is too broad                    | Restrict the policy to the intended principal or role               |
| Access Map is empty               | Test data is missing or incomplete                      | Upload test data that matches the schema                            |
| Impact analysis is incomplete     | Test scenarios do not cover the policy behavior         | Add more test data and rerun impact analysis                        |

## Best practices

| Practice                        | Recommendation                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------- |
| Start with the schema           | Policies should only reference schema-defined entities, actions, and attributes |
| Use clear policy instructions   | Include principal, action, resource, and condition when using AI                |
| Test permit and deny cases      | Validate both allowed and blocked scenarios                                     |
| Review Access Map               | Confirm that policy and data produce the intended access relationships          |
| Review impact before publishing | Check for unintended access changes                                             |
| Keep policies specific          | Avoid broad access unless required                                              |
| Track versions                  | Use Version History to review published changes                                 |
