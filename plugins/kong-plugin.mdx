**Reva AI Runtime Authorization** is an AI Custom Policy for **Kong AI Gateway**. Every OpenAI-style model call, MCP tool call, and A2A agent call that passes through the gateway is evaluated by the [Reva Trust Guardian](/ai-workload-security-overview) before it reaches an upstream, and a denied call never leaves the gateway.

Unlike request-level filtering, the policy evaluates the **delegation chain**. The hops of one agent turn share a trace id and the turns of one chat share a thread id, so a Reva policy can be written against what an agent is doing across a conversation rather than against a single request in isolation.

| Detail | Value |
|:--|:--|
| AI Custom Policy name | `reva-ai-runtime-authorization` |
| Version | `2.0.0` |
| Requires | Kong AI Gateway 2.2 or later |
| Runs as | a streaming or an installed AI Custom Policy |
| Evaluates at | `POST /pdp/ai/access/ai/evaluation` on your Reva host |
| Attaches to | the whole gateway, or an AI Model, AI Consumer, or AI Consumer Group |

Because enforcement lives in the gateway, the application holds no model key and no policy credential. It can only reach a model, a tool, or another agent *through* Kong AI Gateway, so authorization cannot be bypassed by the caller.

## How It Works

```
                     ┌──────────────────────────────┐
                     │   Reva Trust Guardian (PDP)   │
                     │   policies + guardrails       │
                     └──────────────────────────────┘
                                    ▲
                  POST /pdp/ai/access/ai/evaluation
                                    │
  Caller ──▶  Kong AI Gateway  ───────────────▶  Model / MCP server / Agent
             reva-ai-runtime-authorization        (upstream, only on allow)
```

On every request:

<Steps>
  <Step title="Classify the call">
    The policy reads the request body. An OpenAI `messages` array is a model call, a JSON-RPC `tools/call` is a tool call, and an A2A send-message request is an agent call. Anything else is proxied untouched.
  </Step>
  <Step title="Resolve the user">
    The user comes from the `Authorization: Bearer` JWT, in the claim named by `jwt_user_claim`. A request without a usable token is refused with `401`.
  </Step>
  <Step title="Correlate the turn">
    The trace id from the inbound `traceparent` ties the hops of one turn together, and the thread id ties the turns of one chat together. The thread id is sent on the first call of a turn only. The policy keeps no chat history; the Trust Guardian does.
  </Step>
  <Step title="Evaluate">
    The policy sends one evaluation request to the Trust Guardian and waits for a decision.
  </Step>
  <Step title="Enforce">
    An allow proxies the request upstream and attaches a transaction token for the next hop. Anything else ends the request with `deny_status`, unless `monitor_mode` is on.
  </Step>
  <Step title="Summarize the turn">
    When the first call of a trace completes, the policy posts a best-effort summary of the turn to the Trust Guardian so later turns can be evaluated against it. A streamed response is passed through as it is produced and is not summarized.
  </Step>
</Steps>

## Before You Begin

You need:

- **Kong AI Gateway 2.2 or later**, with a Konnect control plane and at least one data plane node.
- **The policy files**, `schema.lua` and `handler.lua`, or the packed `.rock` that contains them. Contact [info@reva.ai](mailto:info@reva.ai) to obtain them.
- **A Reva policy store** with the models, MCP servers, and agents you want to govern, and policies that permit the calls you expect. See [Model your gateway in Reva](#model-your-gateway-in-reva).
- **An authorization token** for the Trust Guardian, from the policy store's [Settings → Connect to Reva Trust Guardian](/ai-workload-developer-settings#connect-your-agents-at-runtime).
- **Outbound HTTPS** from every data plane node to your Reva host.

<Note>
  The policy sends no policy store field of its own. The token decides which policy store a call is evaluated against, so use the token issued by the **policy store you want the gateway evaluated against**.
</Note>

## Set Up

Setting up the policy takes four steps: register it as an AI Custom Policy, attach it as an AI Policy, prepare the gateway entities, and make sure your application forwards the right headers.

### Step 1: Register the AI Custom Policy

Kong AI Gateway runs a custom policy in one of two ways. Reva AI Runtime Authorization works with either.

| | Streaming | Installed |
|:--|:--|:--|
| Where the code lives | Konnect stores it and sends it to every data plane | You put it on every data plane yourself |
| Data plane image | Unchanged | Custom image, or LuaRocks install |
| What Konnect receives | `schema.lua` and `handler.lua` | `schema.lua` only |
| Updating the policy | Update it in Konnect | Rebuild or reinstall, then restart each node |

<Tabs>
  <Tab title="Streaming">
    1. Start every data plane node with these two settings:

       ```bash
       KONG_CUSTOM_PLUGIN_STREAMING_ENABLED=on
       KONG_UNTRUSTED_LUA=lax
       ```

       The first lets the node accept custom policies from Konnect. The second is needed because the policy makes an outbound HTTPS call to the Trust Guardian, which the default `strict` Lua sandbox does not allow.

    2. Create the AI Custom Policy in Konnect, with kongctl, or with the AI Gateway API:

       | Field | Value |
       |:--|:--|
       | `name` | `reva-ai-runtime-authorization` |
       | `type` | `streaming` |
       | `schema` | the contents of `schema.lua` |
       | `handler` | the contents of `handler.lua` |

       ```bash Konnect API
       jq -n --rawfile schema schema.lua --rawfile handler handler.lua \
         '{name: "reva-ai-runtime-authorization", type: "streaming",
           display_name: "Reva AI Runtime Authorization",
           schema: $schema, handler: $handler}' |
       curl -X POST "https://<region>.api.konghq.com/v1/ai-gateways/<ai-gateway-id>/custom-policies" \
         -H "Authorization: Bearer $KONNECT_TOKEN" \
         -H "Content-Type: application/json" \
         --data @-
       ```
  </Tab>
  <Tab title="Installed (Docker)">
    1. Build a data plane image that contains the policy, and run every node from it:

       ```docker
       FROM kong/kong-ai-gateway:2.3.0-distroless

       COPY kong/plugins/reva-ai-runtime-authorization /usr/local/share/lua/5.1/kong/plugins/reva-ai-runtime-authorization

       ENV KONG_PLUGINS=bundled,reva-ai-runtime-authorization
       ```

    2. Create the AI Custom Policy in Konnect with `name` `reva-ai-runtime-authorization`, `type` `installed`, and `schema` set to the contents of `schema.lua`. Do not send a `handler`.
  </Tab>
  <Tab title="Installed (LuaRocks)">
    1. On every data plane node, install the policy:

       ```bash
       luarocks install kong-plugin-reva-ai-runtime-authorization-2.0.0-1.all.rock
       ```

    2. Add it to the `plugins` directive in `kong.conf`, then restart the node:

       ```yaml
       plugins = bundled,reva-ai-runtime-authorization
       ```

    3. Create the AI Custom Policy in Konnect with `name` `reva-ai-runtime-authorization`, `type` `installed`, and `schema` set to the contents of `schema.lua`. Do not send a `handler`.

    A code change needs a restart, not only a configuration sync. The gateway loads Lua when a worker starts.
  </Tab>
</Tabs>

<Note>
  The `name` must be `reva-ai-runtime-authorization`, the name declared in the schema. Neither `name` nor `type` can be changed after the AI Custom Policy is created.
</Note>

### Step 2: Attach the Policy

Create an AI Policy whose type is `reva-ai-runtime-authorization`. Only `auth_token` is required; set `reva_host` unless your tenant is on `api.reva.ai`.

<CodeGroup>
```json Global
{
  "name": "reva-runtime-authorization",
  "type": "reva-ai-runtime-authorization",
  "global": true,
  "config": {
    "reva_host": "api.example.reva.ai",
    "auth_token": "{vault://env/reva-ai-runtime-authorization-token}"
  }
}
```

```bash Konnect API
curl -X POST "https://<region>.api.konghq.com/v1/ai-gateways/<ai-gateway-id>/policies" \
  -H "Authorization: Bearer $KONNECT_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "reva-runtime-authorization",
    "type": "reva-ai-runtime-authorization",
    "global": true,
    "config": {
      "reva_host": "api.example.reva.ai",
      "auth_token": "{vault://env/reva-ai-runtime-authorization-token}"
    }
  }'
```
</CodeGroup>

A **global** policy covers every model, MCP server, and agent on the gateway, which is what you want when the gateway is the only way to reach them. To govern part of your traffic instead, leave `global` off and reference the policy from the entity it should cover.

<Warning>
  Leave the policy's **Condition** empty. A condition that names a variable the data plane does not know stops the whole configuration from syncing, and Konnect then shows the node as **Sync pending**.
</Warning>

### Step 3: Prepare the Gateway Entities

Each upstream you want governed is an entity on the gateway: a model, an MCP server, or an agent. The policy needs two things from them.

- **Request buffering stays on.** The policy reads the request body, so `request_buffering` must be enabled on the routes it covers. It is on by default.
- **MCP responses are not buffered.** MCP servers stream over SSE, so `response_buffering` must be disabled on MCP routes.

Authenticate callers before their requests reach the policy, for example with a key or OpenID Connect policy. This policy decodes the user's JWT to read claims but does **not** verify its signature.

### Step 4: Forward the Headers From Your Application

The policy can join the hops of one turn only if every service in the chain passes on what it received. Each agent must send these headers, spelled as shown, on every call it makes through the gateway: to a model, to an MCP server, and to another agent.

| Header | Send it | What it does |
|:--|:--|:--|
| `Authorization: Bearer <JWT>` | on every call | Names the user. The policy decodes it and reads [`jwt_user_claim`](#jwt_user_claim). Forward the end user's token unchanged; a service token in its place attributes the call to the service. A call without it is refused with `401`. |
| `traceparent` | on every call | The W3C trace context. Its 32-character trace id is what makes separate calls one turn. The first service starts one for each user message, and every later call forwards it unchanged. If it is missing the policy creates one, and Reva cannot link the call to the turn it belongs to. |
| `X-Transaction-Token` | on every call after the first | The Trust Guardian issues it when it allows a call, and the policy adds it to the request it sends upstream. Forward it exactly as received on every call that follows. Its presence tells the policy that the call is a later hop. |
| the thread id, at the place [`session_key`](#session_key) names (default: the header `X-Reva-Session-Id`) | on the first call of a turn only | Groups the turns of one chat. Later hops do not need it. |

For one turn, the calls carry:

```
user  ->  agent A     Authorization: Bearer <JWT>
                      traceparent: 00-<trace id>-<span id>-01
                      X-Reva-Session-Id: <chat id>         (named by session_key)

agent A  ->  agent B  Authorization: Bearer <JWT>          (the same token)
                      traceparent: 00-<trace id>-<span id>-01   (the same trace id)
                      X-Transaction-Token: <token>         (from the request A received)

agent B  ->  model    Authorization: Bearer <JWT>
                      traceparent: 00-<trace id>-<span id>-01
                      X-Transaction-Token: <token>         (from the request B received)
```

`X-Reva-Session-Id` is only the default name. The thread id is read from whatever [`session_key`](#session_key) names: a header of another name, or a field in the JSON body such as `params.message.contextId`. Send it where that setting points.

Each hop passes on the transaction token it received. The policy issues a new one for every call it allows and puts it on the upstream request, so the value an agent forwards is always the one on the request it was just handed.

<Warning>
  An agent that drops `X-Transaction-Token` makes its next call look like a first call made by the user. An agent that drops `traceparent` splits one turn into several. Both weaken what a Reva policy can see, without producing an error. An agent that drops `Authorization` is refused.
</Warning>

#### How the policy tells the first call from a later one

A call that carries no `X-Transaction-Token` is the first call of a turn. A call that carries one is a later hop. The Trust Guardian draws the same line: a transaction token exists only because an earlier call was evaluated and allowed.

| | First call of a turn | Later hop |
|:--|:--|:--|
| Identifies the user | `subject` and `principal` from the JWT | none sent; Reva takes the agent and the user from the token |
| Thread id | sent, when `session_key` finds one | not sent; Reva joins the call to its thread through the trace id |
| Summary of the turn | posted when the call completes, unless the response is streamed | not posted |

#### If a header is missing

None of these produces an error in your application. The turn just becomes harder for Reva to follow.

| Missing | What happens |
|:--|:--|
| `Authorization` | The call is refused with `401` and the reason `missing Authorization bearer token`. Reva is not called. |
| `traceparent` | The policy creates a new trace, so Reva cannot link the call to the turn it belongs to. |
| `X-Transaction-Token` on a later hop | The call is evaluated as a first call made by the user, not as a nested hop made by the agent. Its thread id is sent again, so a different id would record it under another thread. |
| the thread id on the first call | The turn has no thread id, so Reva cannot join it to earlier turns of the chat. |

#### Token lifetime

A transaction token is short-lived, and Reva sets the lifetime for your deployment. A service that waits too long between receiving a request and making its next call, for example behind a slow model or a cold start, finds the token expired. Reva then refuses the call: the response carries `authorization service unavailable`, and the data plane log shows `X-Transaction-Token validation failed`. Keep the time between hops short rather than retrying with the same token.

## Model Your Gateway in Reva

A Reva policy matches the resource the policy sends. Register your models, MCP servers, and agents in the policy store so they line up with what the gateway reports.

| Call | Action | Resource in Reva | Where it comes from |
|:--|:--|:--|:--|
| Model | `invokeModel` | `Model::"gpt-4o"` | the `model` field of the request body |
| Tool | `invokeTool` | `Tool::"ticketing-mcp/open_ticket"` | the tool name from `params.name`, joined to the MCP server whose base URL matches the gateway entity's upstream URL |
| Agent | `invokeAgent` | `Agent::"https://ticketing-agent.example.com"` | the upstream URL of the gateway entity, as `protocol://host[:port]` |

- **MCP servers.** Register each MCP server in Reva with the same base URL as its upstream on the gateway. The policy sends the tool name and that URL; the Trust Guardian resolves the URL to the MCP server and names the tool `<mcp server>/<tool>`.
- **Agents.** An agent is identified by its upstream URL alone — never a path, and never the path the caller used. Two agents are two upstreams on two hosts.
- **Models.** A request with no usable `model` is reported as `unknown-model`, which no policy matches, so it shows up in the decision log rather than passing silently.

## Configuration Reference

Every field is set under the AI Policy's `config`. `auth_token` is the only required field.

### Connection

| Field | Type | Default | Purpose |
|:------|:-----|:--------|:--------|
| `reva_host` | string | `api.reva.ai` | Host or base URL of your Reva tenant |
| `auth_token` | string | **required** | Token the gateway presents to the Trust Guardian |
| `ssl_verify` | boolean | `true` | Verify the Trust Guardian's TLS certificate |

#### reva_host

Host or base URL of your Reva tenant, for example `api.example.reva.ai`. A host-only value is called over HTTPS; a full URL such as `https://api.example.reva.ai` is used as given, and trailing slashes are trimmed.

The policy evaluates every call at `/pdp/ai/access/ai/evaluation` on this host. The path is not configurable.

<Warning>
  An empty value falls back to `api.reva.ai`. If your tenant is on another host, an empty or mistyped `reva_host` sends evaluations to the wrong place and every call is refused with `authorization service unavailable`.
</Warning>

```json
{ "reva_host": "api.example.reva.ai" }
```

#### auth_token

Token the gateway presents to the Trust Guardian on every evaluation. Copy it from the policy store's [Settings → Connect to Reva Trust Guardian](/ai-workload-developer-settings#connect-your-agents-at-runtime).

The field is **referenceable**. In production, give it a vault reference rather than a literal, so the secret never appears in a configuration export.

```json
{ "auth_token": "{vault://env/reva-ai-runtime-authorization-token}" }
```

<Warning>
  This token is a secret with policy-evaluation rights. Never commit or log it. Rotate it from the same Settings panel if it is exposed.
</Warning>

#### ssl_verify

Verify the TLS certificate presented by the Trust Guardian. Defaults to `true`.

Turn it off **only** against a test instance with a self-signed certificate. With it off, the gateway cannot tell your Trust Guardian from anything that can intercept the connection.

### Enforcement

| Field | Type | Default | Purpose |
|:------|:-----|:--------|:--------|
| `monitor_mode` | boolean | `false` | Evaluate and log, but never block |
| `fail_open` | boolean | `false` | Proxy when no decision could be obtained |
| `deny_status` | integer | `403` | HTTP status returned on a refusal |
| `deny_message` | string | `Blocked by Reva` | Message returned on a refusal |

#### monitor_mode

Evaluate every call and log the verdict, but never block. Defaults to `false`.

This is the natural first step of a rollout: attach the policy to real traffic, see what *would* have been refused, then turn it off to enforce. A would-be denial is logged at `warn`:

```
[reva-ai-runtime-authorization] MONITOR would deny invokeTool open_ticket for alice:
           authorization denied by policy (proxying anyway)
```

<Note>
  `monitor_mode` decides what to do with a decision Reva **gave**. `fail_open` decides what to do when Reva could not be **reached**. They are independent.
</Note>

#### fail_open

Proxy the request when the Trust Guardian cannot be reached or returns no decision. Defaults to `false`, so an outage refuses calls rather than passing them unevaluated.

The policy allows 5 seconds per evaluation attempt and makes up to three attempts, so `fail_open` only comes into play once all of those have failed.

Setting it to `true` proxies unauthorized agentic traffic during an outage and should be a deliberate, documented choice.

#### deny_status

HTTP status returned when a call is refused, either by policy or because no decision could be obtained. Defaults to `403`; any value from `100` to `599` is accepted.

Change it when a client library treats `403` specially and you would rather it saw a different status for a policy refusal.

<Note>
  The `401` refusals the policy raises **before** calling Reva — a missing token, an unusable JWT — keep their own status. `deny_status` does not apply to them.
</Note>

#### deny_message

Message returned to the caller in the response body when a call is refused. Defaults to `Blocked by Reva`. The specific `reason` is returned alongside it:

```json
{ "message": "Blocked by Reva", "reason": "authorization denied by policy" }
```

Unlike `deny_status`, this message also applies to the pre-evaluation `401` refusals.

### Identity

| Field | Type | Default | Purpose |
|:------|:-----|:--------|:--------|
| `jwt_user_claim` | string | `sub` | JWT claim identifying the user |
| `jwt_groups_claim` | string | `groups` | JWT claim holding the user's group memberships |

#### jwt_user_claim

JWT claim read from the inbound `Authorization: Bearer` token to identify the user. Defaults to `sub`. Common alternatives are `preferred_username` and `cognito:username`.

- **Nested claims** use a dotted path: `user.id`.
- **Colon-style keys** such as `cognito:username` are a single claim name, not a path.
- The policy **decodes** the JWT payload; it does not verify the signature. Authenticate callers before their requests reach it.

On the first call of a turn, this user is sent as both `subject` and `principal`. On a nested hop — one that carries an `X-Transaction-Token` — the policy sends neither, and the Trust Guardian takes the calling agent and the user from the token.

A missing token, an unreadable JWT, or an empty claim is refused with `401` before Reva is called. There is no header fallback: the user comes from the token, or the request does not proceed.

```json
{ "jwt_user_claim": "preferred_username" }
```

#### jwt_groups_claim

JWT claim holding the user's group memberships, read from the same token. Defaults to `groups`.

| Identity provider | Typical value |
|:--|:--|
| Generic OIDC | `groups` |
| RBAC-style tokens | `roles` |
| Keycloak | `realm_access.roles` |
| Amazon Cognito | `cognito:groups` |

The user's token is forwarded to the Trust Guardian with every evaluation, so group claims travel with it.

### Payload

| Field | Type | Default | Purpose |
|:------|:-----|:--------|:--------|
| `prompt_key` | string | `content` | Field carrying the prompt text in the evaluation request |
| `session_key` | string | `X-Reva-Session-Id` | Header or body field carrying the chat or thread id |

#### prompt_key

Names the field carrying the prompt text in the evaluation request. Defaults to `content`.

The policy places the prompt under this key and tells the Trust Guardian where to find it. Change it only when your Reva policies were authored against a different field name; the two must match.

What is sent as the prompt:

| Call | Prompt |
|:--|:--|
| Model | The text of the **last user message** in `messages`. A message whose `content` is an array of parts has its text parts joined; image and audio parts are not sent. |
| Tool | The tool arguments, as `name=value` pairs. |
| Agent | The message's `parts` (`params.message.parts`, or `message.parts` over HTTP+JSON), joined with newlines: each text part's `text`, and each data part as its JSON text, up to 8192 bytes. File parts are not sent. |

#### session_key

Where the policy reads the chat or thread id, which groups separate turns into one conversation. Defaults to `X-Reva-Session-Id`. The name is only a label: it can be any header name or body field your application already uses.

The policy looks at this name and nowhere else, in this order:

1. A request **header** with this name.
2. The JSON **body**. A name with dots is a path from the root of the body, so `params.thread_id` is `body.params.thread_id`. A name without dots is a field at the top of the body.

| Your application sends the chat id as | Set `session_key` to |
|:--|:--|
| the header `X-Reva-Session-Id` | `X-Reva-Session-Id` (the default) |
| another header | its name, for example `X-Acme-Conversation-Id` |
| an A2A `contextId`, over JSON-RPC | `params.message.contextId` |
| an A2A `contextId`, over HTTP+JSON | `message.contextId` |
| a field of your own in the body | its path, for example `params.thread_id` |

The thread id is read and sent to Reva on the **first call of a turn only**. Later hops carry the transaction token and are joined to the thread through the trace, so a different value on a later hop is ignored.

A first call that carries nothing at that name has no thread id, so the Trust Guardian cannot join it to earlier turns. Making every message of a chat carry the same value is the single highest-value change a calling application can make.

```json
{ "session_key": "params.message.contextId" }
```

### Data Plane State and Diagnostics

| Field | Type | Default | Purpose |
|:------|:-----|:--------|:--------|
| `hop_ttl` | integer | `3600` | Seconds an unfinished turn is remembered |
| `forward_traceparent` | boolean | `true` | Pass `traceparent` to the upstream |
| `debug` | boolean | `false` | Log extra diagnostics |

#### hop_ttl

How long, in seconds, a data plane node remembers which call started a turn when that call never finishes. Defaults to `3600`; accepts `60` to `86400`.

The node notes the first call of each trace so that only that call summarizes the turn. The note is removed as soon as the call completes; `hop_ttl` only clears one left behind by a crash or a refused call. Set it comfortably longer than your slowest agent turn.

<Note>
  This note is local to one data plane node and needs nothing declared for it. Send the hops of a trace through the same node, and avoid configuration changes while turns are in flight.
</Note>

#### forward_traceparent

Pass the `traceparent` used for the authorization decision on to the upstream service. Defaults to `true`, so one trace id spans the gateway, your backend, and the Reva decision log.

Turn it off only if an upstream rejects trace headers.

#### debug

Log extra diagnostics at `notice` level: the reason a request was **skipped** — proxied without being evaluated — and each turn summary as it is sent. Defaults to `false`.

Use it when a call you expected to be evaluated is passing through untouched. Leave it off in production.

## How a Call Is Classified

The policy does not use path prefixes. It classifies from the request body, in this order:

| Request | Action | Evaluated |
|:--|:--|:--|
| JSON-RPC `tools/call` | `invokeTool` | Yes |
| JSON-RPC `message/send`, `message/stream`, `SendMessage` or `SendStreamingMessage`, or an HTTP+JSON `POST` to `…/message:send` or `…/message:stream` | `invokeAgent` | Yes |
| Any other JSON-RPC method | — | No, proxied untouched |
| OpenAI `messages` array | `invokeModel` | Yes |
| Anything else | — | No, proxied untouched |

Of the MCP methods only `tools/call` is evaluated; discovery calls such as `initialize` and `tools/list` pass through.

### A2A requests

An agent call is any A2A request that sends a message to an agent. The policy evaluates it in both protocol versions and both bindings:

| Operation | JSON-RPC method, 0.3 | JSON-RPC method, 1.0 | HTTP+JSON path ends with | Response |
|:--|:--|:--|:--|:--|
| Send a message | `message/send` | `SendMessage` | `/message:send` | one reply |
| Send a message, streamed | `message/stream` | `SendStreamingMessage` | `/message:stream` | server-sent events |

- **HTTP+JSON** is recognized by the end of the path, so a version or tenant prefix such as `/v1/message:send` or `/acme/message:send` is fine. The body is the request itself, `{"message": {...}}`, with no JSON-RPC envelope.
- **Media type.** A body is read as JSON for any JSON media type, including `application/a2a+json`, which A2A 1.0 recommends for HTTP+JSON.
- **Streamed responses** are passed through as they are produced. The policy does not buffer them, so the turn is not summarized to the Trust Guardian. The evaluation of the call itself is unchanged.
- **Not evaluated:** requests that read or manage tasks (`tasks/*`, `GetTask`, `CancelTask`, `SubscribeToTask`, and the push-notification configuration methods), agent-card requests, the gRPC binding, and JSON-RPC batches.

## What Reva Sees

For each evaluated call the policy sends one request to `/pdp/ai/access/ai/evaluation`.

| Header | Value |
|:--|:--|
| `X-API-Token` | `Bearer` plus `auth_token` |
| `Authorization` | The end user's JWT, as received |
| `X-Transaction-Token` | The token from the previous hop, when the request carried one |
| `X-Reva-Thread-Id` | The thread id, on the first call of a turn, when one was found |
| `traceparent` | The inbound trace context, or one created for this turn |

The first call of a turn, from a user to an agent:

```json
{
  "content": "Open a ticket for my duplicate charge",
  "rtg/a2a": {
    "action":   { "name": "invokeAgent" },
    "resource": { "type": "Agent",
                  "id": "https://billing-support-agent.example.com",
                  "endpoint": "https://billing-support-agent.example.com" },
    "subject":   { "type": "User", "id": "alice" },
    "principal": { "type": "User", "id": "alice" },
    "transmission": { "promptKey": "content", "role": "agent",
                      "content": "Open a ticket for my duplicate charge" },
    "threadId": "471e538c-bcda-4690-81d4-efbba8573e20",
    "session":  { "id": "471e538c-bcda-4690-81d4-efbba8573e20" }
  }
}
```

A nested tool call made later in the same turn, carrying the transaction token:

```json
{
  "content": "summary=Duplicate charge issue, customer_id=alice",
  "rtg/a2a": {
    "action":   { "name": "invokeTool" },
    "resource": { "type": "Tool", "id": "open_ticket",
                  "endpoint": "https://ticketing-mcp.example.com" },
    "transmission": { "promptKey": "content", "role": "agent",
                      "content": "summary=Duplicate charge issue, customer_id=alice" }
  }
}
```

What each part carries:

- **`content`** — the prompt, under the key named by `prompt_key`. It is repeated in `transmission.content`.
- **`resource`** — what is being called. Tool and agent calls also carry `endpoint`, the upstream URL of the gateway entity.
- **`subject` and `principal`** — the user, on the first call of a turn only. A nested hop sends neither.
- **`threadId` and `session.id`** — the thread id, on the first call of a turn only, when one was found.

On an allow, the Trust Guardian returns a transaction token. The gateway adds it to the upstream request as `X-Transaction-Token`, and the upstream forwards it on its own calls.

## When a Call Is Refused

A refused call ends at the gateway with `deny_status` and `deny_message`, and the upstream is never contacted. The body carries a `reason` naming the specific case:

| Status | Reason | Meaning |
|:--|:--|:--|
| `deny_status` | `authorization denied by policy`, or the reason Reva returned | Reva evaluated the call and refused it |
| `deny_status` | `authorization service unavailable` | No decision was obtained from the Trust Guardian |
| `deny_status` | `could not build authorization request` | The policy could not encode the evaluation request |
| `401` | `missing Authorization bearer token` | No bearer token was presented |
| `401` | `Authorization bearer token is not a JWT` | A bearer was presented but could not be decoded |
| `401` | `jwt claim ... is empty` | The JWT decoded, but `jwt_user_claim` held no value |

Applications should surface these differently: a policy denial has a matching row in the [decision logs](/decision-logs), the others have none. The `401` refusals are raised before Reva is called, so they are unaffected by `fail_open`, `monitor_mode`, or `deny_status`.

## Guardrails

Policies are not the only thing that can refuse a call. A policy store can also carry [guardrails](/guardrails/overview) — content-level evaluators such as intent-drift detection and jailbreak or prompt-injection checks, configured in the Reva console rather than here.

**Nothing in this policy configures them, and nothing needs to.** Guardrails run inside the same evaluation, and their verdict is folded into the single decision the gateway receives. From the gateway's point of view a guardrail denial is indistinguishable from a policy denial: same status, same `reason`, same fail-closed behavior.

The [decision logs](/decision-logs) record evaluated policies and evaluated guardrails separately, so an operator can see which of the two refused a request. If a call is being blocked and no policy explains it, look at the guardrails before changing policy.

## Verify the Setup

<Steps>
  <Step title="Send a call with no bearer token">
    The policy should refuse it itself, which proves it is loaded and running. Use the route of one of your models:

    ```bash
    curl -i -X POST https://<gateway-host>/<model-route>/chat/completions \
      -H 'Content-Type: application/json' \
      -d '{"model":"gpt-4o","messages":[{"role":"user","content":"hi"}]}'
    ```

    ```
    HTTP/1.1 401
    {"message":"Blocked by Reva","reason":"missing Authorization bearer token"}
    ```

    If another policy authenticates callers on that route, add its credential so the request reaches this one.
  </Step>
  <Step title="Repeat with a JWT">
    Add a bearer token carrying the claim named by `jwt_user_claim`:

    ```bash
    curl -i -X POST https://<gateway-host>/<model-route>/chat/completions \
      -H 'Authorization: Bearer <jwt>' \
      -H 'Content-Type: application/json' \
      -d '{"model":"gpt-4o","messages":[{"role":"user","content":"hi"}]}'
    ```
  </Step>
  <Step title="Check the decision">
    Each evaluated call is logged on the data plane, and each decision appears in the Reva [decision logs](/decision-logs):

    ```
    [reva-ai-runtime-authorization] evaluating invokeModel gpt-4o payload={...}
    [reva-ai-runtime-authorization] invokeModel gpt-4o allowed=true status=200 latency_ms=412.3
    ```

    The first line is logged at `notice` and includes the prompt text. The second is logged at `info`, so set `KONG_LOG_LEVEL=info` to see it.
  </Step>
</Steps>

## Troubleshooting

### The data plane shows "Sync pending"

The data plane rejected the configuration, so nothing you changed in Konnect is live.

- Check the data plane log for the rejected field. A `config` field the schema does not define is reported as `unknown field`; this happens when the AI Custom Policy's schema was updated but an existing AI Policy still carries fields from the earlier schema. Remove them from the policy's `config`.
- Clear the policy's **Condition** if it names a variable the data plane does not support.

### Every call is refused with "authorization service unavailable"

No decision is reaching the gateway. The data plane log names the cause:

| Log line | Cause |
|:--|:--|
| `no decision (RTG returned HTTP 404)` | `reva_host` points at a host that does not serve the evaluation path. Check for an empty or mistyped value. |
| `no decision (RTG returned HTTP 401: ...)` | `auth_token` was rejected, the user's token is not a well-formed JWT, or a forwarded transaction token has expired. The message names the header that failed. |
| `RTG call attempt N failed` | The data plane cannot reach the Reva host. Check outbound HTTPS. |

A genuine policy denial always has a row in the decision log. These do not.

### A call late in a turn is refused

The response says `authorization service unavailable` and the data plane log shows `HTTP 401: ... X-Transaction-Token validation failed`. The transaction token the agent forwarded has expired. This happens when an agent takes a long time between receiving a request and making its next call. Shorten the delay — for example by keeping services warm — rather than retrying with the same token.

### The policy is not found, or requests fail with 500

- **Streaming:** start every data plane node with `KONG_CUSTOM_PLUGIN_STREAMING_ENABLED=on` and `KONG_UNTRUSTED_LUA=lax`.
- **Installed:** put `handler.lua` and `schema.lua` on **every** data plane node, and make sure `KONG_PLUGINS` includes `reva-ai-runtime-authorization`. Konnect only holds the schema.
- **Installed:** restart the node after a code change.

### Calls are proxied without being evaluated

- Turn on `debug`; a skipped request logs the reason.
- Only MCP `tools/call`, A2A send-message requests (see [A2A requests](#a2a-requests)), and OpenAI-style `messages` requests are evaluated. Task requests, agent-card requests, and JSON-RPC batches pass through.
- Confirm the policy is attached to the entity the call is routed to, or is global.

### Turns are not joined into one conversation

- Confirm every agent forwards `traceparent` and `X-Transaction-Token` unchanged.
- Confirm the first call of every turn carries the same thread id for a chat, at the header or body field that [`session_key`](#session_key) names.
- Send the hops of a trace through the same data plane node.

### MCP calls fail with "Session terminated"

- Keep `request_buffering` enabled on the route — the policy reads the request body.
- Disable `response_buffering` — MCP streams over SSE.

## A Rollout That Works

<Steps>
  <Step title="Observe">
    Attach the policy with `monitor_mode: true`. Nothing is blocked; the log and the decision log show what *would* have been refused.
  </Step>
  <Step title="Tune policy">
    Work through the would-be denials in the [decision logs](/decision-logs) until the verdicts match your intent.
  </Step>
  <Step title="Enforce">
    Set `monitor_mode: false` and leave `fail_open: false`.
  </Step>
  <Step title="Harden">
    Authenticate callers in front of the policy, and move `auth_token` into a vault reference.
  </Step>
</Steps>
