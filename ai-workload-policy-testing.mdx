Test your agentic policies the same way they'll run — as decisions on individual hops in an agent chain. Catch a too-broad or too-narrow policy before it reaches production.

## Why Test Agentic Policies

A single user request can fan out into many agent-to-agent and agent-to-tool calls. A policy that looks right in isolation can still block a legitimate chain — or allow one it shouldn't. Testing lets you confirm each hop resolves the way you expect.

## Test an Agent-Chain Decision

1. Open the policy store and go to the **Policies** tab, then choose **Test**.
2. Build the request you want to evaluate:
   - **Principal** — the caller (e.g., `Agent::"shipment-supervisor-agent"`).
   - **Action** — `invokeAgent`, `invokeTool`, or `invokeModel`.
   - **Resource** — the target (e.g., `Agent::"billing-agent"` or `MCP::"reva-rate-mcp"`).
3. Add **context** the way it arrives at runtime — `onBehalfOf` (the delegating user and attributes such as `riskTier`), `environment` (time, IP, geo), and any custom values your policies test (e.g., `container_id`).
4. Run the evaluation and read the decision — **Allow** or **Deny** — along with the policy that determined it.
5. Repeat for each hop in the chain (User → Agent, Agent → Agent, Agent → Tool) to confirm the whole flow behaves as intended.

## Simulate Before Publishing

Use the Policy Designer's **Test** and **Impact** controls to simulate changes against your modeled topology before publishing. This shows which calls a new or edited policy would newly allow or deny.

## Validate with the Access Map

The **Access Map** visualizes the resulting access relationships — for example, `shipment-supervisor-agent → invokeTool → reva-rate-mcp`. Use it to confirm that intended paths are permitted and unintended ones are not.

## Validation Checklist

Before you publish, confirm:

1. Each entity referenced by a policy exists in the schema and topology.
2. Every intended hop (user→agent, agent→agent, agent→tool/model) returns **Allow**.
3. Every unintended hop returns **Deny** (fail-closed).
4. Context-based conditions (`context.*`) match the values your agents actually send.
5. On-behalf-of conditions resolve against the right `context.onBehalfOf` attributes.
6. Intent-based conditions align with the caller's permitted intents.
7. Results appear as expected in the [decision logs](/ai-workload-decision-logs) after a test run.
